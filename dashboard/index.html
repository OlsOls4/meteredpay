Pay per successful agent call — nothing for a failed call.

A buyer prepays testnet NEAR into a contract. A successful call deducts 0.1 testnet NEAR. A failed call is released — held amount released, never deducted. An over-budget call is refused on-chain. This page is read-only: it never signs, never sends a transaction, and never asks for a private key or seed phrase.

What is sold: the seller is a JSON schema-validation service (meteredpay-schema-validate) — it checks a document against a fixed schema and returns valid/invalid plus an error list. A document that fails validation is a real failure: the call is never deducted. Send a document with the wrong type (a number where text is required) and the buyer pays nothing for it.

Who it helps: a buyer agent that pays per API call only pays for calls it can verify, and a seller is paid 0.1 testnet NEAR per successful call — a failed call deducts nothing from the buyer and earns the seller nothing, so neither side chases payment for work that did not check out.

Succeeded

Deducted 0.1 testnet NEAR — only after the buyer verified the seller signature.

Failed

Refunded — held amount released, never deducted. The buyer submits a failure claim; that claim releases the hold.

Refused

Over budget — refused on-chain. A successful transaction with an on-chain refusal record; balances unchanged.

Steps, in execution order — one command runs them all

  1. Deposit. Run node buyer/buyer.mjs --buyer <buyer>.testnet --mode demo --tag demo once. This one command deposits 0.5 and sets cap 0.2 first, then runs the five calls in steps 2–6 below in order — do not run it again per step. (Or deposit and set the cap yourself with the commands in README §2.5, then run the same command with --skip-setup.) See: deposited 0.5, held 0, spent 0, available 0.5, cap 0.2. Proof: your deposit transaction on the explorer.
  2. Success deducts. The script's first call: one success call. See: Succeeded — deducted 0.1 testnet NEAR; spent 0.1, available 0.4. Proof: deduction transaction, e.g. BD3fkPVQ… (canonical replay; your run has its own hash).
  3. Fail releases. The script's second call: one fail call. See: Failed — held amount released, never deducted; spent still 0.1, available still 0.4. The buyer submits a failure claim; that claim releases the hold. Proof: release transaction, e.g. 3a6juX9u….
  4. Timeout releases. The script's third call: one timeout call; wait 30 s. See: Failed — no receipt received: held amount released, never deducted; balances unchanged. Proof: release transaction, e.g. C2EXM52z….
  5. Success deducts again. The script's fourth call: one more success call. See: Succeeded — deducted 0.1; spent 0.2 (= cap), available 0.3. Proof: deduction transaction, e.g. C34RNjN1….
  6. Over budget refused. The script's fifth and last call: one more success call. See: Refused — over budget; amount 0 — refused; balances unchanged. This is a successful transaction with an on-chain refusal record. Proof: refusal transaction, e.g. ESem4Kum….

Final state after steps 1–6: deposit 0.5 / held 0 / spent 0.2 / available 0.3 / cap 0.2. Invariant at every step: available = deposit − spent − held. A call that costs exactly your available budget succeeds. Shorter core: --mode replay runs deposit, two successes, refusal only. No key, token, or permission from the builder is needed; one judge's replay does not disturb another's (state is per buyer). Full setup commands are in README §2.3 and §2.5.
